00Executive Summary

One assistant, five departments, zero email chains

Employees today email HR for a leave policy, email IT for a laptop, and email Admin for a visitor pass. This platform replaces all three inboxes with one conversational front door — backed by real company data, not guesses.

In plain English: the system is built from three layers. A front door (the chat interface employees actually use), a brain (a router that decides which specialist should answer, then 13 specialists who each know one domain deeply), and a memory (company documents and HR records, converted into a searchable form the AI can read accurately instead of guessing).

It is deliberately not one giant AI trying to know everything — that approach hallucinates under pressure. It is a small team of narrow experts, coordinated by a dispatcher, each backed by verified source documents.

03Repository Structure

Where everything lives

The repository mirrors the architecture diagram — each top-level folder is one layer or one concern. Nothing is scattered.

aa-hackathon/ ├── apps/ # everything that runs │ ├── web-ui/ # Layer 1 — React 18 + Vite front end │ │ └── src/ │ │ ├── components/ # ChatWindow, EscalationDrawer, FormsDrawer… │ │ ├── modules/ # onboarding-guidance, analytics, COO views │ │ ├── services/ # API clients │ │ └── config/ # MSAL / env config │ ├── api-gateway/ # Layer 2+3+4 — FastAPI backend │ │ └── app/ │ │ ├── main.py # app entry point │ │ ├── agents/ # supervisor_agent.py (MasterAgent) + 12 domain agents │ │ ├── api/ # auth · controllers · repositories · services │ │ ├── rag/ # retriever.py — the ONLY module allowed to query pgvector at runtime │ │ └── memory/ # client.py, md_store.py, complexity.py, enrichment.py │ └── jobs/ # Layer 5 — scheduled / batch work, never called live │ ├── sharepoint_ingestion/ # SharePoint → chunk → embed → pgvector │ └── run_all_ingestion.py ├── integrations/ # thin external-system clients │ └── sharepoint/client.py ├── deployments/ # infrastructure as config │ └── docker/docker-compose.yml # api + postgres(pgvector) + redis └── knowledge-specs/ # specification-first documentation (11 sections) └── docs/00-foundation/ … 10-reference/
The rule behind the structure: jobs/ is the only place allowed to talk to SharePoint. Live agents never call SharePoint directly — they only ever query PostgreSQL/pgvector through app/rag/retriever.py. This one rule is what keeps chat response times fast and SharePoint outages from ever taking down the assistant.

05Why This Architecture

Five properties an enterprise buyer checks for

Scalable

Agents are added, not rewired — a new domain (Finance, in Phase 2) is a new agent extending BaseDeepAgent plus a routing rule, not a change to the other 13. Retrieval, LLM inference, and the database each scale independently since they're separate services.

Maintainable

One rule — "SharePoint is only touched inside jobs/" — means a SharePoint outage or schema change never breaks live chat. Shared base classes mean a bug fix in retrieval logic fixes it for all 13 agents at once, not 13 separate patches.

Enterprise-ready

Identity runs through Azure AD/MSAL — no parallel password system. Every action writes to audit_logs. PII has its own detection and redaction trail. Guardrails run in two tiers before any model call.

Easy to onboard into

Specification-first: every capability is documented under knowledge-specs/ before it's coded, so a new engineer reads intent before reading Python. The folder layout is the architecture diagram — there's no hidden mental map to transfer.

Reduces technical debt

Skills (retrieval, generation, integration actions) are defined once and composed inside agents rather than copy-pasted — the same pgvector search skill backs all 13 agents. One shared interface contract per skill means fixes don't fork.

Cost-disciplined

Single LLM call per query and a self-hosted model (Ollama, not a per-token external API) keep the platform's unit economics predictable at scale — a deliberate architectural constraint, not an afterthought.

06ML Self-Learning Loop

The system gets better from being used

This is the "good thinking" layer non-technical stakeholders usually ask about last but care about most: does this thing improve on its own, or does it stay exactly this smart forever?

Employee rates a response 👍/👎writes to feedback table
↓
Evaluation framework aggregates signalper-agent accuracy, low-confidence clusters
↓
Retrieval threshold already self-corrects livesimilarity < 0.10 → automatic query reformulation + retry
↓
Low-confidence clusters flagged for SharePoint content ownerscloses gaps in the knowledge base, not just the model
↓
Phase 3 — fine-tuned domain LLMtrained on accumulated HR/IT query-answer pairs

Two feedback loops run today, and one is planned. Fast loop (live): every single query already self-corrects — if retrieval confidence is below the 0.10 similarity floor, the agent automatically reformulates and retries before ever calling the LLM. Slow loop (weekly): thumbs-up/down feedback plus escalation outcomes are aggregated by the evaluation framework to find which question types the assistant answers worst — that becomes a prioritized content backlog for HR/IT document owners, not a mystery. Planned loop (Phase 3): once enough real query/answer/feedback triples accumulate, they become training data for a domain fine-tuned model, reducing reliance on generic prompting over time.

Why this is the right shape for "self-learning" here: a support assistant that silently retrains itself on live traffic is a governance risk in HR/IT — wrong answers could get reinforced. Human-reviewed, evaluation-gated improvement is slower but auditable, which matters more for a system touching payroll and access provisioning.
